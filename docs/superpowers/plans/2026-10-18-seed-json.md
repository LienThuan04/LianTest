# Editable JSON seed implementation plan

> **For agentic workers:** Use superpowers:executing-plans to execute this existing seed refactor inline in the user's current checkout. Implementation preserved the checkout without commits/pushes; the user later explicitly requested committing and pushing all completed work on 2026-10-18.

**Goal:** Move every editable seed row to JSON under `src/seed-db/data`, with common loading/validation functions used by startup and both seed scripts.

**Architecture:** Preserve Prisma models, runtime/API behavior, password hashing, skip-existing defaults and explicit clear flags. Load JSON only when seeding/checking, validate shapes and references before any write/clear, and ship data with the production build. A source-data directory takes priority during local use so JSON edits do not need recompilation; optional `SEED_DATA_DIR` selects an entire custom dataset.

**Spec:** User request: editable JSON data in the seed-db module's `data` directory; users can customize seed data without editing application code. Existing code defines the current seed semantics.

**Tech stack:** NestJS/TypeScript, Node fs, Prisma, existing Jest; no new dependencies.

## Constraints and rulings

- User specified the data location and JSON/functions split; proceed within that scope without another permission cycle.
- Preserve all current seed content exactly (including the approved `@liantest.vn` emails), IDs and relative-hour date offsets.
- Validate before writes or clear-and-seed, including CLI paths. Disabled startup seeding must not parse JSON.
- Schema/DB business modules, auth, frontend, lockfiles and other work-in-progress are outside this refactor.
- Existing databases are skipped, not silently synchronized or reset after JSON edits.
- Source and built JSON must work; no import-time cached constants or source-only production dependency.

## Review focus

1. Malformed JSON, wrong primitives, duplicate keys, dangling references and insufficient automatic question counts fail before DB mutations.
2. Custom account/course/group/question IDs are honored; no implicit gv001/sv001 dependencies in the seeder.
3. Startup clear validates first, both CLI scripts use the same dataset, and explicit clear-only keeps its existing behavior.
4. Source edits are read on every seed/check invocation; packaged-only deployment can locate copied JSON.
5. Disabled seed stays independent of missing/invalid optional data; loaded user passwords remain environment configuration and are hashed.
